# Wyrmwatch 0.2.8

Windows app updates now use the installed application path, keeping desktop and
Start menu shortcuts on the updated build. Download and update verifies an
Ed25519-signed catalog and package checksum, releases the background manager
gracefully, shows installer progress and reopens the same workspace automatically.
The game process remains independent. Busy operations and installed services
continue to require an idle/manual service handoff.

Application-owned files are backed up and verified before replacement. A separate
helper restores the previous application if installation or file verification
fails. Saves, game files and credentials are excluded from application recovery.
Existing shortcut arguments are preserved; the active workspace is explicit so
relaunching from a shortcut retains connections even under packaged launchers.

## One-time migration from older releases

Versions through 0.2.7 shipped an updater that launches a portable workspace copy.
Run this release's Windows setup program once to establish the corrected installed
update flow. Close the old Wyrmwatch application when idle; the game can keep
running. Future installed releases update through Download and update. Portable
and service installations retain their explicit installation/service handoff.

This release retains the 0.2.7 credential-recovery, Activity scrolling and
persistent Follow log fixes. Game-side removal of AdminPassword remains an
inference; an already lost password must be saved once. Linux packages remain
preview builds with the existing package/portable handoff. No automatic service,
game startup, live credential migration or world modification is performed by
the app installer. Keep independent world backups.

Versions before 0.2.7 did not retain AdminPassword separately from the game INI.
If it was already missing before the first save/start with 0.2.7 or later, enter
it once in Server settings while stopped. Later app updates preserve that saved
credential in the same workspace. Windows DPAPI remains tied to the account that
saved it; service-owned values are read through the authenticated owning agent.
